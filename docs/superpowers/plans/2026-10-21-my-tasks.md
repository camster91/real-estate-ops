# Tasks: "My Tasks" API (#44, first slice) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A signed-in member can list the tasks assigned to them in an organisation and create a task for themselves. Every creation writes its audit event and outbox event in the same transaction.

**Architecture:**
- **New package `@reo/domain`:** holds the shared task rules (statuses, title and due-date validation), so the web app and worker never re-implement them.
- **Migration `0006_tasks.sql`:** adds `task`.
  - RLS lets a member see only tasks assigned to them or created by them.
  - The runtime role may insert only tasks that it creates for itself.
  - No UPDATE yet.
- **Two API routes,** both built on `inTenant` (ADR 0013):
  - `GET /v1/organizations/:organizationId/tasks`
  - `POST /v1/organizations/:organizationId/tasks`

  The POST inserts the task and calls `recordChange` (ADR 0014) in one transaction. A client-supplied task id makes a retried POST safe.

**Tech Stack:** Fastify 5 JSON schema validation, PostgreSQL 16, Vitest 5. No new dependencies.

**Spec:**
- `docs/product/CORE_MODEL.md`: "Task: ready/in_progress/waiting/blocked/completed/cancelled. Dependency completion and responsible owner required…"; "Home shows personal priorities".
- `docs/platform/M1_PLAN.md`, "Suggested first vertical slice": "read a tenant-scoped assigned work summary … A reversible internal synthetic task creation adds mutation, audit and outbox atomically."
- AGENTS.md: "Shared domain schemas; no duplicate business rules"; "Idempotent integration handlers and jobs"; "Outbox/event pattern".
- ADRs 0010, 0013 and 0014.
- Owner decisions (21 October 2026): build in two steps (audit and outbox first, now merged in #135); a task is visible to its assignee and its creator only.

**Out of scope (later plans):**
- The web "My tasks" screen and web sign-in. The next plan adds both, because the web app needs a same-origin sign-in first.
- Status changes and editing (UPDATE).
- Assigning tasks to other people (#32, and needs the #24 role rules).
- Dependencies, checklists, templates and recurrence (#43–#46).
- Manager and team views.

## Decisions for owner approval

1. **Visibility.** A task is visible only to its assignee and its creator. RLS enforces this, not only the API.
2. **Self-assigned creation only.** A member may create tasks only for themselves. An active membership is the only requirement: this is an internal, reversible action on operational data, so no record grant applies.
3. **New tasks start as `ready`, with classification `operational`.**
   - The title is plain text of 1–200 characters, with no control characters.
   - The due date is optional, must be a valid date-time, and is stored in UTC. The web app shows it in America/Toronto later.
4. **The title never goes into audit or event data.** It is free text, so minimisation would redact it anyway. The audit details record only `status` and `hasDueDate`.
5. **Safe retries.** The client sends a fresh UUID `id` with each new task.
   - Sending the same `id` again returns the existing task with 200, with no second task, audit or event.
   - The same `id` with a different title gives 409 `conflict`.

## Global Constraints

- Strict TypeScript, Biome and exact pins. Forward-only migration `0006`; do not edit `0001`–`0005`.
- `task` follows the existing pattern: `ENABLE` and `FORCE ROW LEVEL SECURITY`, policies in the `(SELECT app.fn())` shape, and a composite `(organization_id, id)` primary key. The assignee and creator are composite FKs to `membership (organization_id, principal_id)`.
- Routes use `requireSession` then `inTenant` with the purpose constant `"operations"`. The tenant and actor never come from the body.
- Errors use fixed codes: `invalid_task` (400), `conflict` (409), `not_found` (404), `authentication_required` (401), `forbidden_origin` (403).
- Logs carry no titles, task ids or organisation ids.
- The audit action is `task.create`, the event is `task.created` (schema version 1, aggregate version 1), and the payload is `{ taskId }`.
- Use synthetic data and Canadian spelling.

## Review Focus

1. **Another member's task.** It never appears in the list, even when it is in the same organisation. Test in Task 2 (DB) and Task 3 (HTTP).
2. **Creating a task for someone else.** A body `assigneeId`, or a raw insert with another assignee, is refused (the schema rejects unknown fields, and RLS refuses the insert). Test in Tasks 2 and 3.
3. **Retried POST.** The same `id` twice gives one task, one audit row and one event. The same `id` with a different title gives 409. Test in Task 3.
4. **Odd titles.** Empty, whitespace-only, 201 characters, or containing control characters or NUL give 400 `invalid_task`, never 500. Emoji and accented letters are accepted. Test in Tasks 1 and 3.
5. **Membership lost mid-flight.** After suspension, the list returns 404 and nothing is created. Test in Task 3.

### Task 1: `@reo/domain` task rules

**Files:**
- Create: `packages/domain/package.json` (name `@reo/domain`, same shape as `@reo/config`), `packages/domain/tsconfig.json`, `packages/domain/src/index.ts`, `packages/domain/src/task.ts`, `packages/domain/src/task.test.ts`
- Modify: `pnpm-lock.yaml` (run `pnpm install`), and `vitest.config.ts` only if `packages/**` does not already cover the new tests

**Interfaces:**
- Produces:
  - `TASK_STATUSES: readonly ["ready", "in_progress", "waiting", "blocked", "completed", "cancelled"]`
  - `type TaskStatus = (typeof TASK_STATUSES)[number]`
  - `TITLE_MAX = 200`
  - `interface NewTask { id: string; title: string; dueAt: Date | null }`
  - `parseNewTask(input: unknown): { ok: true; task: NewTask } | { ok: false; field: "id" | "title" | "dueAt" | "body" }`, which:
    - trims the title
    - accepts only `{ id, title, dueAt? }` (any other key gives `body`)
    - requires `id` to be a UUID, which is lower-cased
    - accepts a `dueAt` that is `null`, absent, or an ISO 8601 date-time string with an offset or `Z`; anything else gives `dueAt`

### Task 2: `task` table

**Files:**
- Create: `packages/db/migrations/0006_tasks.sql`, `packages/db/src/tasks.db.test.ts`

**Interfaces:**
- **`task` columns:**
  - `organization_id uuid NOT NULL REFERENCES organization`
  - `id uuid NOT NULL`
  - `title text NOT NULL CHECK (char_length(title) BETWEEN 1 AND 200 AND title !~ '[[:cntrl:]]' AND btrim(title) = title)`
  - `status text NOT NULL DEFAULT 'ready' CHECK (status IN ('ready','in_progress','waiting','blocked','completed','cancelled'))`
  - `assignee_principal_id uuid NOT NULL`
  - `created_by_principal_id uuid NOT NULL`
  - `due_at timestamptz CHECK (due_at IS NULL OR isfinite(due_at))`
  - `classification text NOT NULL DEFAULT 'operational' CHECK (classification IN ('operational','personal','financial','restricted_compliance'))`
  - `version integer NOT NULL DEFAULT 1 CHECK (version >= 1)`
  - `created_at timestamptz NOT NULL DEFAULT now()`
  - `PRIMARY KEY (organization_id, id)`
  - composite FKs from `(organization_id, assignee_principal_id)` and `(organization_id, created_by_principal_id)` to `membership (organization_id, principal_id)`
  - index `task_assignee` on `(organization_id, assignee_principal_id, status, due_at)`
- **Policies:**
  - `task_read` `FOR SELECT TO reo_app USING (organization_id = (SELECT app.current_organization_id()) AND (SELECT app.has_active_membership()) AND (SELECT app.current_principal_id()) IN (assignee_principal_id, created_by_principal_id))`
  - `task_create_own` `FOR INSERT TO reo_app WITH CHECK (organization_id = (SELECT app.current_organization_id()) AND (SELECT app.has_active_membership()) AND created_by_principal_id = (SELECT app.current_principal_id()) AND assignee_principal_id = (SELECT app.current_principal_id()))`
- **Grants:** `SELECT` on `task`, and column-level `INSERT (organization_id, id, title, assignee_principal_id, created_by_principal_id, due_at)` to `reo_app`. So status, classification, version and `created_at` always take their defaults on insert.

  - `table is forced and not owned by the runtime role`.

### Task 3: Task routes

**Files:**
- Create: `apps/api/src/tenant/tasks.ts`, `apps/api/src/tenant/tasks.db.test.ts`
- Modify: `apps/api/src/tenant/routes.ts` (call `registerTaskRoutes`), `apps/api/package.json` (add `@reo/domain`), `pnpm-lock.yaml`

**Interfaces:**
- Consumes: `parseNewTask` and `TaskStatus` (Task 1), the `task` table (Task 2), `inTenant`/`NOT_MEMBER` and `requireSession` (ADR 0013), and `recordChange`/`DuplicateEventError` (ADR 0014).
- Produces:
  - `registerTaskRoutes(app: FastifyInstance, options: { pool: pg.Pool }): void`
  - `GET /v1/organizations/:organizationId/tasks` returns 200 `{ tasks: [{ id, title, status, dueAt, version }] }`:
    - only tasks where `assignee_principal_id` is the current principal
    - ordered with open statuses (not `completed` or `cancelled`) first, then `due_at` ascending with nulls last, then `created_at`
    - `LIMIT 100`, `Cache-Control: no-store`, and `dueAt` as an ISO string or null
  - `POST /v1/organizations/:organizationId/tasks` takes the body `{ id, title, dueAt? }`:
    - 201 `{ task }` for a new task
    - 200 `{ task }` for a replay with the same id and the same title and due date
    - 409 `{ error: "conflict" }` for the same id with different content
    - 400 `{ error: "invalid_task", field }` for invalid input
    - 404 for a non-member

    Inside one `inTenant` transaction it runs `INSERT … ON CONFLICT (organization_id, id) DO NOTHING RETURNING *`. If a row is returned, it calls `recordChange({ action: "task.create", resourceType: "task", resourceId: id, details: { status: "ready", hasDueDate }, event: { type: "task.created", schemaVersion: 1, aggregateVersion: 1, payload: { taskId: id } } })`. Otherwise it SELECTs the existing row (visible only to its creator) and compares it. If no row is visible, the id belongs to another member's task in the same organisation, and the response is 409 `conflict`, without revealing anything about that task.
  - The Fastify `bodyLimit` for the POST is 4 KB. Parsing is done by `parseNewTask`, not a duplicated JSON schema.
